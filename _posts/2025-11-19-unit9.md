Unit 9 expanded understanding of how different Database Management Systems (DBMSs) support data storage, processing, and large-scale analytics. The unit contrasted the limitations of traditional file-based data storage with modern database approaches. Traditional systems treat each application as an isolated data silo, producing redundancy and high maintenance costs, while DBMS environments centralise shared data, enforce standards, and preserve integrity (Connolly and Begg, 2015).

The unit explored several database models including relational, object-oriented, and non-relational architectures. **Relational databases**, structured around tables, keys, and constraints, remain dominant for transactional workloads where consistency is critical (Date, 2019). **NoSQL systems**, such as MongoDB, prioritise schema flexibility and horizontal scalability, making them suitable for semi-structured or rapidly evolving datasets (Meier and Kaufmann, 2019). The comparison clarified why technology choice must be driven by application context rather than general performance assumptions.

These principles linked directly to the **Electricity Bill Management System (EBMS)** project. Consistent customer records, meter readings, and billing transactions require strict integrity rules. Transactional accuracy, multi-table joins, and foreign-key enforcement all aligned naturally with a relational solution. This rationale supported the selection of PostgreSQL for the group system design and SQLite for the unit practical work, both of which implement full SQL standards and ACID transaction support (Russell, 2021).

Core modelling techniques were revised through **Entity-Relationship Diagrams (ERDs)** and relational schema design. ER modelling enabled complex business domains to be decomposed into entities, attributes, and relationships, later translated into tables governed by primary and foreign keys (Cleve and Hainaut, 2012). This methodology reinforced earlier normalisation tasks by demonstrating how logical data models feed directly into physical database implementation.

Transaction processing and concurrency control formed another major theme. In multi-user environments, unregulated interleaving of operations can produce anomalies such as lost updates, dirty reads, or inconsistent analysis. DBMS platforms safeguard integrity through transaction scheduling strategies, isolation levels, locking protocols, and commit/rollback mechanisms (Elmasri and Navathe, 2016). These safeguards ensure databases remain logically consistent even during peak access conditions — a capability essential to operational systems like EBMS.

The unit also introduced **big-data architectures** that extend beyond classical DBMS structures. Lambda and Kappa frameworks were presented as dual pathways for managing historical batch analytics and real-time streaming data. Such architectures illustrate how organisations integrate relational stores with distributed processing systems to achieve both responsiveness and accuracy (Kleppmann, 2017). These concepts provided useful context for understanding how IoT platforms, data lakes, and machine-learning pipelines coexist alongside conventional SQL databases.

The practical aspect of Unit 9 involved storing previously cleaned UNICEF data in SQLite using Python interfaces. This exercise demonstrated how theoretical modelling translates into real database creation, table population, and query execution. Performing joins, data aggregation, and integrity checks consolidated understanding of how scripts interact directly with database engines.
