Unit 11 focused on how database systems maintain data reliability during concurrent access and unexpected failures. Central to this topic is the **ACID transaction model — Atomicity, Consistency, Isolation, and Durability —** which defines the conditions required for safe and recoverable database operations (Date, 2019). Atomicity ensures that multi-step transactions are fully applied or fully rolled back; consistency enforces that integrity constraints remain valid; isolation prevents interference between overlapping transactions; and durability guarantees that committed changes persist even in the event of system failure.

The unit highlighted the technical challenges that emerge in multi-user environments where transactions are **interleaved**. Without appropriate controls, concurrency may lead to anomalies such as **lost updates, dirty reads, non-repeatable reads, or phantom reads** (Connolly and Begg, 2020). These risks are mitigated through scheduling strategies including serialisable transaction ordering, **locking mechanisms**, and carefully configured **isolation levels** that balance data protection with system performance.

The process of failure recovery was introduced through core techniques including **write-ahead logging, checkpoints, rollback and redo operations**. These mechanisms allow the database engine to reconstruct a **consistent state** after crashes or interruptions by replaying committed changes and undoing uncommitted ones (Elmasri and Navathe, 2016). The **transaction manager** coordinates these activities and enforces integrity across routine operations and recovery procedures, making it a pivotal component of high-availability database systems.

## Evaluation — Final EBMS Project vs Initial Proposal

Unit 11 also provided the opportunity to critically review the completed **Electricity Bill Management System (EBMS)** project against the original proposal developed during **Unit 6**. The initial proposal prioritised building a relational schema capable of managing customer accounts, meter readings, billing periods, payments and staff administration using PostgreSQL. The core objectives were strong normalisation (to 3NF), regulatory compliance, and role-based access controls.

While the final project delivered a schema aligned with these goals, the evaluation identified gaps in its **report structure and explanatory depth**. The most significant issue raised by tutor feedback concerned **organisation and clarity** rather than technical correctness. The justification for selecting an SQL RDBMS was introduced prematurely, before the conceptual and logical modelling stages had been properly explained. As González-Pérez and Henderson-Sellers (2018) note, effective database documentation should follow a logical flow from abstraction to implementation, mirroring the design lifecycle itself. Revisiting Unit 11 reinforced how the report disrupted this sequence.

Another limitation identified was the **underdevelopment of the data pipeline narrative**. The project lacked sufficient emphasis on **staging tables, validation rules, and error-handling mechanisms**, which are particularly relevant to transaction-heavy environments such as billing systems. As seen in real operational contexts, transformations from raw meter readings to structured billing records must incorporate verification layers to ensure referential accuracy and protect against duplication or partial updates (Connolly and Begg, 2020). Such processes align closely with ACID principles but were under-articulated in the written submission.

Unit 11 clarified how transactional reliability connects to the EBMS use case directly. Billing systems rely on batching, reconciliation, dispute resolution processes and payment rollbacks — all of which depend upon atomic updates and durable commit states. Without emphasising these links within the project evaluation, the narrative risked presenting normalisation and schema design as conceptual exercises rather than operational necessities.

## Artefactual Evidence

Two core artefacts were produced during the normalisation and implementation processes:

- **unit7_normalisation.sql** — documentation of the original denormalised table decomposition into 1NF, 2NF and 3NF relational structures.
- **unit7_sql.sql** — full SQL database build script implementing table definitions, keys and constraints within SQLite.

Testing confirmed that **foreign-key constraints and transactional dependencies were enforced correctly**, with failed delete or update actions blocked where referential conflicts existed. These practical validations demonstrated how conceptual transaction theory translated into tangible database behaviour.

## Learning Integration

Unit 11 consolidated the understanding that **transaction management is not an abstract database concept but the operational backbone of any reliable data system**. The interdependence between schema design, access concurrency, and failure recovery became more apparent when viewed alongside the EBMS project outcomes. The limitations identified in the written evaluation reinforced how critical it is not only to design functional systems but also to communicate how theoretical principles apply to real-world workflows.
