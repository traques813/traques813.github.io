Unit 10 examined how **Application Programming Interfaces (APIs)** enable structured communication between software systems and how these mechanisms support large-scale data collection, parsing, and sharing. The client-server model forms the basis of most modern APIs: a server exposes defined endpoints, and a client application retrieves or modifies resources using standardised web protocols. Most APIs rely on **HTTP**, using request methods such as **GET, POST, PUT and DELETE**, supported by headers and payload bodies that control how data is exchanged (Fielding and Taylor, 2002).

The unit highlighted the importance of **machine-readable data formats**, particularly **JSON and XML**, which allow information to be transferred efficiently without relying on fragile scraping workflows. JSON is widely adopted due to its lightweight syntax and natural fit with programming language objects, while XML remains relevant where strict schema supervision or legacy integrations are required (Nurseitov et al., 2009). Headers such as `Content-Type` and `Accept` allow clients and servers to negotiate compatible formats and prevent parsing failures.

Different categories of APIs were explored — **internal, public, partner and composite APIs** — each reflecting distinct governance requirements. Public APIs prioritise accessibility and rate management, while internal and partner APIs typically enforce stricter authentication and access segmentation. Composite APIs streamline system performance by bundling multiple requests into unified calls (Fryer, 2021).

**Authentication and authorisation mechanisms** were a core focus. While Basic Authentication and static API keys offer simple access controls, they were shown to present considerable security risks if leaked or reused across services. **OAuth 2.0** emerged as the dominant industry standard, enabling token-based access delegation without sharing account credentials and allowing granular restriction of API permissions through scoped authorisations (Hardt, 2012).

API architectural design was examined through **REST principles**, which structure web services around resource endpoints rather than operations. RESTful models improve interoperability and scalability by separating concerns between clients and servers, leveraging stateless communication and predictable uniform interfaces (Fielding, 2000). This paradigm dominates contemporary web integration, including data pipelines that feed applications, dashboards, and machine-learning systems.

The unit also addressed **real-time integration methods**, including polling, long polling, and webhooks. Traditional polling allows clients to periodically query changes but becomes inefficient at scale. Long polling improves responsiveness by delaying server responses until updates occur, while webhooks enable near-instant server-initiated notifications by registering client callback endpoints (Pautasso et al., 2012). Each technique balances latency, bandwidth efficiency, and complexity, depending on deployment constraints.

Security remained a continual thread throughout the unit. Exposed APIs increase system attack surfaces and must be protected against unauthorised access, malformed queries, denial-of-service behaviour, and injection attacks. Effective controls include encrypted transport (HTTPS/TLS), input validation, schema enforcement, key rotation policies, strict logging, and rate limiting (OWASP, 2023). These controls ensure both **confidentiality** and **integrity** of personal or business-critical data during transfer.

## Artefactual Engagement — API Security Specification

This unit’s practical activity required writing a **security requirements specification** for an API used by an electricity-billing organisation integrating with Python scripts and structured data formats (JSON, XML, and an SQL backend). The specification outlined key protective controls:

- **OAuth 2.0 authentication** with defined role scopes separating meter-read services from billing and analysis dashboards.
- **Schema validation** of JSON/XML payloads at the API boundary to reject malformed or suspicious input.
- **Secure XML parser configurations** preventing entity expansion and potential XXE vulnerabilities.
- **Exclusive use of parameterised SQL queries** or stored procedures to protect against injection.
- **Rate-limiting and pagination controls** to prevent mass data enumeration.
- **Encrypted transport (TLS)** for all interactions.
- **Minimal logging policies** with partial data masking for privacy compliance.

This artefact illustrated how API connectivity intersects directly with regulatory compliance, cybersecurity practice, and data-governance principles rather than operating as a simple data-collection tool.
