Unit 7 connected database theory directly to hands-on system construction, consolidating the conceptual work from Unit 6 through two practical tasks: a formal **normalisation exercise** and the **implementation of a working SQL database**. The combination of these activities showed how database structure emerges progressively rather than appearing fully formed at the coding stage.

The first task involved normalising a supplied unstructured dataset that stored multiple values within individual records, including lists of courses, teachers, and exam boards aligned to each student. This violated First Normal Form (1NF), which requires that table attributes be atomic and contain single values only (Date, 2013). To address this, repeating groups were separated so each row represented one student-course-board-teacher relationship.

Transitioning to **Second Normal Form (2NF)** required identifying partial dependencies. Attributes such as student name and date of birth depended solely on the StudentID rather than on the combined composite key used at 1NF. These attributes were therefore relocated to a dedicated student table to remove redundancy and dependency issues (Connolly & Begg, 2015).

The final stage involved applying **Third Normal Form (3NF)** to remove transitive dependencies — most notably the repeated association of courses with the same teachers and exam boards. Lookup tables were introduced to model these relationships independently, leaving only foreign key references in linking tables. This final design ensured that each fact was stored once and only once, reducing update anomalies and improving overall referential integrity (Elmasri & Navathe, 2016).

---

## SQL Database Implementation

The second task transformed the 3NF design into a functional database using SQLite. Tables were created according to the final schema, each with defined **primary keys**, and relational constraints were enforced using **foreign keys**. Referential integrity testing was conducted by attempting invalid record deletions and insertions — operations were correctly rejected by the DBMS, validating that table dependencies were properly enforced (Coronel & Morris, 2019).

SQL joins spanning multiple tables were executed to verify that relational links behaved as expected and that the decomposed structure successfully reconstructed original views of the dataset without introducing ambiguity or duplication. This step confirmed the central purpose of normalisation: ensuring that data integrity is preserved even when information is separated across independent entities.

Through the implementation phase it became clear that the preceding modelling work significantly reduced development complexity. Once the dependency logic had been fully resolved in the conceptual phase, SQL definitions followed a predictable structure rather than requiring iterative trial-and-error adjustments. This aligned with guidance found in database engineering literature: logical schema validation should precede physical implementation to avoid design inversion and structural reworking (Harrington, 2016).

## Reflections on Design and Practice

Completing both tasks together highlighted how closely database theory mirrors professional design workflows. Normalisation provided not only a theoretical framework but also acted as a procedural checklist that guided engineering decisions during schema construction. Working directly with relational constraints clarified how theoretical issues — such as transitive dependencies — manifest practically as redundancy, deletion anomalies, and inconsistent query results.

The unit also reinforced how **earlier data wrangling activities feed forward into modelling work**. Steps such as duplicate removal, consistent formatting, and validation of categorical fields reduced complexity during schema creation. Without these preparatory phases, constraint enforcement becomes difficult or even impossible, illustrating the continuous and cumulative nature of the data pipeline (Kimball & Ross, 2013).

Finally, Unit 7 solidified the understanding that relational database design is not purely a programming exercise. It is an analytical process that integrates conceptual modelling, dependency reasoning, and systematic testing. The experience demonstrated how careful schema construction enables reliable systems without reliance on extensive procedural validation logic or manual correction routines.
